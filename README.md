# Diamonds Price Prediction

## Описание проекта

Цель проекта — решить задачу регрессии на датасете Diamonds и пройти полный классический ML pipeline максимально близко к реальной практике Data Science.

Задача состоит в предсказании цены алмаза (`price`) по его характеристикам: весу, размерам, качеству огранки, цвету, чистоте и другим признакам.

Проект был построен не только ради получения работающей модели, но и ради отработки правильного процесса:

- EDA;
- baseline;
- feature engineering;
- hyperparameter tuning;
- анализ результатов;
- контроль утечек данных;
- разделение логики между ноутбуками и `.py` файлами.

В ноутбуках остаются только загрузка данных, вызовы функций, визуализация и выводы.

## Датасет

Использовался датасет Diamonds.

Основные характеристики:

- около 54 000 строк;
- 10 признаков;
- задача регрессии;
- целевая переменная: `price`.

Числовые признаки:

- `carat`;
- `depth`;
- `table`;
- `x`;
- `y`;
- `z`.

Категориальные признаки:

- `cut`;
- `color`;
- `clarity`.

## EDA

На этапе EDA были изучены распределения признаков, связь признаков с ценой, пропуски, выбросы и потенциальные проблемы качества данных.

Основные выводы:

- пропусков в датасете нет;
- `price` имеет выраженную правостороннюю асимметрию;
- `carat` сильно связан с `price`;
- `x`, `y`, `z` также сильно коррелируют с ценой;
- в признаках `x`, `y`, `z` есть строки, где все три размера равны нулю;
- `depth` и `table` имеют слабую линейную связь с ценой;
- категориальные признаки `cut`, `color`, `clarity` требуют аккуратной интерпретации, так как средняя цена по категориям может быть искажена влиянием веса камня.

По итогам EDA были сформированы гипотезы:

- обработать строки с `x = y = z = 0`;
- проверить `log1p(price)`;
- проверить `log1p(carat)`;
- проверить ordinal encoding для `clarity`;
- добавить `volume = x * y * z`;
- добавить `base_area = x * y`;
- добавить `xy_ratio = x / y`;
- сравнить использование исходных `x`, `y`, `z` и агрегированных геометрических признаков.

## Baseline

На этапе baseline использовались только сырые признаки.

Принцип baseline:

> Не использовать гипотезы из EDA и не применять feature engineering.

Разрешенная обработка:

- `train_test_split`;
- one-hot encoding категориальных признаков.

Категориальные признаки:

- `cut`;
- `color`;
- `clarity`.

Разбиение данных:

```python
train_test_split(
    test_size=0.2,
    random_state=42,
)
```

Тестовая выборка была отложена до финальной оценки.

Для cross-validation использовался:

```python
KFold(
    n_splits=5,
    shuffle=True,
    random_state=42,
)
```

Основная метрика:

```text
RMSE
```

Baseline-модели:

- `DummyRegressor`;
- `LinearRegression`;
- `RandomForestRegressor`;
- `HistGradientBoostingRegressor`.

Результаты baseline показали:

- `DummyRegressor` является нижней границей качества;
- `LinearRegression` существенно уступает ансамблевым моделям;
- `RandomForestRegressor` показывает хороший результат;
- лучший baseline дала модель `HistGradientBoostingRegressor`.

По итогам baseline для дальнейших экспериментов была выбрана модель:

```text
HistGradientBoostingRegressor
```

## Feature Engineering

На этапе feature engineering проверялись гипотезы, сформированные после EDA.

Важно:

> Feature engineering проводился только на train-части данных. Test set не использовался.

Проверенные эксперименты:

- baseline `HistGradientBoostingRegressor`;
- замена `x = y = z = 0` на `NaN`;
- добавление `volume`;
- добавление `base_area`;
- добавление `xy_ratio`;
- добавление всех геометрических признаков;
- добавление `log1p(carat)`;
- ordinal encoding для `clarity`;
- замена исходных `x`, `y`, `z` на агрегированные геометрические признаки;
- комбинация агрегированных геометрических признаков и ordinal encoding для `clarity`;
- трансформация таргета через `log1p(price)`.

Лучший результат показала комбинация:

```text
geometry_without_xyz_plus_ordinal_clarity
```

В этом варианте:

- строки с нулевыми размерами интерпретировались как missing values;
- добавлялись агрегированные геометрические признаки;
- исходные `x`, `y`, `z` удалялись;
- `clarity` кодировался через ordinal encoding.

Результат:

```text
baseline HGBR RMSE: около 560.51
best feature engineering RMSE: около 551.67
```

Улучшение составило примерно:

```text
-8.84 RMSE
```

Вывод:

> Feature engineering дал умеренное улучшение качества. Лучшей схемой признаков стала комбинация агрегированных геометрических признаков и ordinal encoding для `clarity`.

## Hyperparameter Tuning

После выбора модели и схемы feature engineering был выполнен подбор гиперпараметров для `HistGradientBoostingRegressor`.

На этом этапе были зафиксированы:

- модель: `HistGradientBoostingRegressor`;
- preprocessing: `geometry_without_xyz_plus_ordinal_clarity`;
- метрика: RMSE;
- CV: 5-fold KFold;
- test set не использовался.

Подбирались параметры:

- `learning_rate`;
- `max_iter`;
- `max_leaf_nodes`;
- `min_samples_leaf`.

Лучший результат после tuning:

```text
best CV RMSE: около 546.09
```

Лучшие параметры:

```python
{
    "learning_rate": 0.04,
    "max_iter": 250,
    "max_leaf_nodes": 63,
    "min_samples_leaf": 20,
}
```

Сравнение этапов:

```text
baseline HGBR:              RMSE около 560.51
best feature engineering:   RMSE около 551.67
tuned model:                RMSE около 546.09
```

Вывод:

> Подбор гиперпараметров дал дополнительное реалистичное улучшение качества без подозрительно резких скачков.

## Контроль Утечек Данных

Во время проекта был обнаружен важный источник потенциальной утечки данных: техническая индексная колонка случайно попадала в признаки при чтении CSV.

После исправления чтения данных с корректным `index_col` результат стал правдоподобным.

Этот эпизод показал важность sanity checks:

- проверять список признаков перед обучением;
- убеждаться, что `target` не попал в `X`;
- проверять, что технические колонки не используются моделью;
- подозревать слишком хорошие результаты.

## Главные Выводы

- `HistGradientBoostingRegressor` оказался лучшей моделью для этой задачи.
- Ручной feature engineering дал умеренное улучшение.
- Наиболее полезными оказались агрегированные геометрические признаки и ordinal encoding для `clarity`.
- `log1p(carat)` не дал улучшения, так как бустинг уже умеет работать с нелинейностями.
- `log1p(price)` ухудшил RMSE на исходной шкале цены.
- Hyperparameter tuning дал дополнительный прирост качества.
- Контроль утечек данных является обязательной частью ML pipeline.
